# Native wrapping VM recovery status

User requirement: pure independent implementation, no `wrapper.node` runtime dependency.

The outer Hook approach used by ZSign is **not** sufficient. The unresolved byte-identical step is the final custom VM invoked by:

```text
sub_55658EF -> sub_5B62121 -> sub_5B61AFB -> sub_5B64F10
```

## Confirmed call boundary

`sub_55658EF` computes a raw 16-byte MD5 digest, then calls:

```c
NativeResult* sub_5B62121(
    std::string* module_id,
    uint8_t* md5_digest16,
    uint64_t digest_len,   // 16
    uint8_t* extra,        // ""
    uint64_t extra_len     // 0
);
```

Return layout:

```c
struct NativeResult {
    uint32_t len;
    uint8_t* data;
};
```

The caller copies `data[0:len]` as signature part2 and then zeroes/frees the buffer.

## `sub_5B62121`

Builds heap argument blocks:

```c
struct ArgBlock {
    uint32_t len;
    uint16_t type; // 0x1e
    uint16_t pad;
    uint8_t* data;
};
```

Then calls:

```c
sub_5B61AFB(module_id, "LLL", digest_block, extra_block_or_null, ...)
```

## `sub_5B61AFB`

This is the VM launcher:

1. `malloc(0x17a)`
2. `memcpy(program, 0xD57090, 0x17a)`
3. `sub_5B62EE8(ctx, program)`
4. stores/copies `module_id` into context
5. `sub_5B62F7E(ctx, "LLL", va_list)` loads arguments
6. `sub_5B64F10(ctx)` executes bytecode and returns `NativeResult*`

Important: the previous Python fallback returning `digest.hex()` has been removed because it is not byte-identical and would hide the missing VM.

## `sub_5B6D9EB` / opcode `0x77` update

`opcode 0x77` is not a primitive branch/arithmetic operation. It is a compound helper call into `sub_5B6D9EB`.

Main program callsites:

```text

00e2: 77 05 14 00 05 00  # mode 21, salt 0x14b7ba9329e934e3
```

High-level recovered structure:

The 20-byte header object layout is now clear:

```text

0x00    1     constant 0x0c
0x01    1     constant 0x15 on the recovered `LLL` branch
```

Confirmed standard algorithms inside `sub_5B6D9EB`:

* MD5, using standard IV/round constants/padding.

The 8-byte key derivation before RC4 is now more precise:

This matches the byte-shuffling loops around `sub_5B6D9EB` lines 721-963.

## Environment byte / opcode `0x79` and final tail `0x7a`

The environment checks do not change the input MD5.  They change one byte of the
raw 21-byte `r7` VM object that is fed into the final wrapper: `r7[5]`.

Recovered raw assembly in `VM_PROGRAM_MAIN` before the final tail:

```text
r3 = 20-byte native header
r7 = 21-byte raw object
copy r3[0..4]   -> r7[0..4]
copy r3[5..19]  -> r7[6..20]
opcode 0x79     -> r7[5] = environment flags
```

This 21-byte `r7` object is **not** the final returned sign.  The VM continues:

```text
016a: 79 07 15 00 07 00   op_79: mutate r7.data[5]
0170: 7a 07 02 00 27 00   op_7a: r2 = sub_5B7D768(r7.data + 2, slot[2])
0176: 00 02               nop
0178: 61 02               return r2
```

`op_7a` reads its length argument from `slot[2]`; on this path `slot[2] == 20`.
`sub_5B7D768` therefore constructs a 20-byte object from `r7.data + 2`, appends
byte `0x04` as the last byte, then invokes a nested VM with format `"LL"`.  This final VM is **not**
the older 0x16c table previously named `VM_PROGRAM_SECONDARY`; it is `src__2` at
`0xD59790`, copied as `0xCC0` bytes by `sub_5B7D5DC`.  Therefore returning the
raw 21-byte `r7` object is wrong; the final native sign length comes from the
object returned by this `LL` VM.  `sub_55658EF` copies exactly
`*(uint32_t*)ptr` bytes from that returned object.

`sub_5B7D768` exact wrapper:

```python
def sub_5B7D768(src, n=20):
    obj = ArgBlock(len=n, type=0x20, data=bytearray(n + 1))
    obj.data[0:n-1] = src[0:n-1]   # native copies 19 bytes from r7.data+2 here
    obj.data[n-1] = 0x04
    obj.data[n] = 0x00
    return sub_5B7D5DC("LL", obj)  # runs src__2 / 0xCC0 VM
```

The earlier `0x27` interpretation was wrong: those bytes are part of the 6-byte
`op_7a` encoding, but the actual length comes from `slot[2]` via the interpreter
handler.  There is no required 38-byte overread on this path.

### Final `LL` helper progress

`op_70` is now partially resolved.  It decodes four slot operands through
`sub_5B6CBD2`, then calls the function pointer `::sub_5B7CB6C` as:

```c
sub_5B7CB6C(dst_obj.data, src_obj.data + scalar_offset, key_obj.data)
```

`sub_5B7CB6C` is an AES-like 16-byte block transform using four T-tables
(`dword_D57A20`, `dword_D57E20`, `dword_D58220`, `dword_D58620`) and final
S-box table `byte_D58A20`.  It performs an initial byteswapped XOR with four
round-key words, then five loop iterations that contain two table rounds each,
then a final S-box round.  In other words, final `LL` VM uses a table-based AES
primitive rather than a simple byte shuffle.

`sub_5B6CBD2` operand decoder:

```text
mode = word0 >> 12
common result = HIBYTE(word0) & 0xf
v3 = word2
case 1: a2[0] = v3 & 0xf
case 2: a2[1] = (v3 >> 4) & 0xf; a2[0] = v3 & 0xf
case 3: a2[2] = HIBYTE(v3) & 0xf
case 4: a2[3] = v3 >> 12; a2[2] = HIBYTE(v3) & 0xf
case 5: a2[4] = result; a2[3] = v3 >> 12; a2[2] = HIBYTE(v3) & 0xf
```

`op_7b` calls `sub_5B63952(::i1, object.data, scalar)`.  `sub_5B63952` is not a
small VM primitive: it reads environment/files (`fopen`, `fgets`, `strstr`,
`sscanf`) and calls child helpers.  One child, `sub_5B754F0`, is a simple XOR of
a buffer with a repeated big-endian 32-bit integer:

```python
key = i.to_bytes(4, "big")
for j in range(n):
    dest[j] ^= key[j & 3]
```

`sub_5B63952`'s successful data path is now mostly understood.  On first use it
opens `/proc/self/maps`, reads lines with:

```c
sscanf(line, "%lx-%lx %*s %lx %*x:%*x %*d %s%n", &start, &end, &off, path, &n)
```

and only follows mappings whose parsed path contains `"qq"`.  It scans those
mapped address ranges for a 528-byte framed blob:

```text
+0x000: "something magic."      // xmmword_990F60
+0x010: 496-byte payload
+0x200: "end magic things"      // xmmword_98FC90
```

When found, it copies the 496-byte payload into the destination object and then
applies `sub_5B754F0(dest, 496, scalar)`, i.e. repeated big-endian-u32 XOR.  The
Python file now contains `sub_5B63952_extract_magic_table(mapped_bytes, scalar)`
and `sub_5B754F0_xor_u32_be(...)` for this recovered successful path.  A static
scan of the IDB `.rodata` found only the marker constants themselves, not a full
`begin + payload + end` framed blob, so the 496-byte runtime table is probably
generated or present in another `qq` mapping at runtime rather than stored as a
plain contiguous blob in `wrapper.node`.

### src__2 first-pass static map

`src__2` (`0xD59790`, `0xCC0`) begins with slot count `0x35`.  A length-table
linear pass using the currently recovered VM op sizes reaches a `return r0` at
program offset `0xA86`; bytes after that are inline data/constants, not linear
code.  This explains why a naive linear sweep falls into apparent unknown
opcodes inside data.

Current byte scan of `src__2`:

```text
byte 0x70: no occurrences
byte 0x7b: one occurrence at offset 0xB9B, in the post-return data region
byte 0x77: offsets 0xAFE and 0xB9A, also post-return data region
```

So the earlier `op_70/op_7b` helper analysis is a generic interpreter capability
and/or another reachable decoding mode, but it is not visible as literal opcode
bytes on the first-pass `src__2` linear path.  The final `LL` bytecode mostly
uses scalar/object arithmetic opcodes plus inline constant tables.  The next
static task is therefore to extend the Python VM with the extra arithmetic
opcodes that appear before `0xA86` (`0x0c`, `0x13`, `0x17`, `0x18`, `0x1d`,
`0x1f`, `0x2d`, `0x2e`, `0x2f`, `0x38`, `0x39`, `0x3a`, `0x51`, `0x55`, `0x57`,
etc.) and emulate the concrete `LL` path, rather than looking for literal
`0x70/0x7b` bytes in this program.

The interpreter switch at `sub_5B64F10` line ~568 maps opcode bytes directly to
labels.  The following final-LL opcodes are now implemented in Python:

```text
0x0c  rD %= rS                         // signed 32-bit modulo, zero divisor -> 0
0x13  rD = imm8 - rS                   // 32-bit
0x17  rD = rS & imm8                   // 32-bit
0x18  rD <<= (rS & 0x1f)               // 32-bit
0x1d  qword_obj[rObj][rIndex] = rValue
0x1f  2-byte default/no-op on concrete final-LL path
0x2d  qword_obj[rObj][rIndex] = rValue
0x2e  rD = sign_extend_16(imm16)       // qword slot
0x2f  rD = rA & rB                     // qword
0x35  rD &= rS                         // qword compact form
0x38  rD = rA ^ rB                     // qword
0x39  rD = rA << low8(rB)              // qword
0x3a  rD = rA | rB                     // qword
0x51  compact relative branch
0x55  rD |= rS                         // qword compact form
0x57  rD <<= low8(rS)                  // qword compact form
```

Remaining linear final-LL anomalies from the naive non-CFG sweep are `0x9d` and
`0x65`; both occur in regions that may be branch-skipped inline data/control
padding rather than executable instructions.  They should be resolved by running
the concrete CFG path after the `LL` argument loader and `src__2` constant are
wired into Python, not by assuming linear reachability.

* The earlier `0x502..0x51c` blocker was caused by multiple compact-op and VM
  state-model mistakes, not by `0x1f` itself.  Confirmed fixes:
  * native keeps scalar slots and object/type slots separately; Python now tracks
    `obj_slots` separately instead of treating object handles as scalar values.
  * `0x09` is a 2-byte packed in-place dword XOR and advances by one VM word.
  * `0x20` is a 2-byte object length read (`len(obj slot)`), not scalar copy.
  * `0x24` on the final-LL path is a 4-byte dword slot copy (`r[raw1] = r[u16@+2]`).
  * `0x1d` is 4-byte dword immediate shift-left.
  * `0x43` is conditional branch if signed dword slot <= 0.
  * `0x15` is dword multiply by signed immediate byte.
  * `0x1c` is qword right-shift by a slot-sourced shift count.
  * `0x22` copies from a relative inline table (`pc + 2 * rel_words`), not an
    absolute byte offset.
  * type `10` objects are qword arrays and must allocate `8 * count` bytes.
  * `0x1f` is 2-byte padding/no-op on this concrete path; treating it as a
    4-byte instruction misaligns the following `0x20` object-length read.
  * `0x07` remains a high-risk opcode: native switch labels indicate compact
    add, but the final-LL byte sequence also contains 4-byte subtract-looking
    forms such as `07 c6 32 06`.  Current code follows the switch-label compact
    add after oracle review; verify against native traces before claiming
    byte identity.
  * `0x35` is a 2-byte compact qword AND, not a 4-byte instruction; decoding it
    as 4 bytes swallows the following `0x1b` and zeroes much of the final block.
  * VM objects now track logical length separately from backing length.  This is
    required for type `10` qword arrays (`logical=count`, backing=`8*count`) and
    changes the final `LL` result length from the erroneous 256 bytes to 32.
  * Object slot copy opcodes `0x26`/`0x28` must alias the same native object slot
    handle.  Deep-copying those slots breaks the rolling state update pattern.
  * Native `sub_5B62E30` checks a per-slot object flag and indexes an object
    table.  The important implementation detail is that the bytecode can write
    scalar values into a still-object-flagged slot (`r0 = len(obj r0)`,
    `r4 = 16`) and later use that slot as an object again.  Python now models
    this with separate scalar slots and object-index slots (`obj_indices`):
    scalar writes do not destroy the object binding.  `sub_5B63780/sub_5B749DE`
    were decompiled directly from IDA: `sub_5B749DE` is vector find + append
    (no replacement/reuse), and `sub_5B63780` sets the object flag then stores
    the returned table index.  The apparent scalar/object-slot conflict is
    explained by `sub_5B62F12` allocating `uint32_t[2*slot_count+1]`; Python
    models the second bank with `obj_indices`.  `0x26/0x28` alias the existing
    object index.
  * `0x20` is a 2-byte object header-length read (`*obj`), not a CRC helper and
    not a 4-byte instruction.  The CRC-like object scan is opcode `0x78`.
  * `0x33` is not allocation in the native switch; it is an object read variant
    through the same object-indexing family as `0x32`.  Allocation is handled by
    `0x21` on this path.  The disassembler text and interpreter were corrected.
  * Compact qword ops were re-audited against native labels:
    `0x35` = `dst &= src`, `0x55` = `dst |= src`, `0x56` = `dst ^= src`,
    `0x57` = `dst <<= low8(src)`.  All use the packed `((word >> 5) & 0x78)` /
    `((word >> 9) & 0x78)` slot fields except `0x57`'s destination nibble.
  * Branch ops on the final `LL` path: `0x50` is signed int8 word-relative
    branch (despite Hex-Rays printing an unsigned byte load), `0x51` is signed
    int16 word-relative branch, and `0x40` compares compact dword slots with a
    signed int32 interpretation before applying a signed int16 word offset.

`dword_79ED398` is set before the VM by the `dladdr` image-path check in

`"wrapper.node"`; otherwise it is `1` and `sign[5] |= 0x08` for non-login

The `login` / `Login` module-name check gates the deeper anti-tamper bits:

```python
flags = 1 if madvise_success else 0
```

So the same raw MD5/header bytes produce different final signatures because

image + non-QQ process + `dword_79ED4F0=1` + invalid global path yields raw
`r7[5] == 0x8f` for non-login modules.

## VIPII opcode progress

The `VM_PROGRAM_VIPII` linear disassembly is now aligned through both executable
blocks.  Important opcode confirmations from `sub_5B64F10`:

* `0x22` is a 6-byte inline-table fill.  Native computes
  `table = current_ip + rel_words`, then copies `table[1] * table_dword[1]`
  bytes from `table + 8` into the destination object.
* `0x34` is a 4-byte signed division: `r[dst] = r[src] / imm8`.  VIPII uses it
  as `r5 = r10 / 2`.
* `0x40` is a conditional branch: compare two scalar registers and branch when
  `lhs >= rhs`.
* `0x42` is a conditional branch using equality/byte-equality semantics.
* `0x50` is a short relative branch.  In the VIPII loops, `50 ea` and `50 ec`
  are signed negative word offsets back to the loop body.
* `0x63` terminates the nested VM with a null native return; VIPII uses it as
  the block end before the embedded alphabet tables.
* `0x73` seeds libc `rand()` from a decoded slot operand (`srand(...)`).
* `0x74` writes libc `rand()` into the selected slot and is 6 bytes long.

The `VIPII` format argument mapping is now recovered from `sub_5B62F7E` and the
callsite in `sub_5B61F70`:

```text
format "VIPII" skips the first byte as a return marker.
remaining "IPII" initializes VM slots 8..11:
    r8  = integer seed passed to srand()
    r9  = mutable output object copied from the src pointer
    r10 = output length
    r11 = mode selector
```

The first branch compares `r11` with `21`; mode 21 executes block 1.  The second
block compares `r11` with `20`; mode 20 executes block 2.  Other modes fall
through into table data and are not valid for the observed native caller.

The first VIPII block now reads as two loops:

```text
allocate 50-byte alphabet object
fill alphabet from embedded table at 0x124 -> VIPII_ALPHABET_20
allocate a 2-element int/index object
fill it from embedded table [0, 1]
r4 = 0
r5 = r10 / 2
srand(r8)
r6 = 0

while r6 < r5:
    r7 = rand()
    r4 = r7 % 50
    r7 = alphabet[r4]
    r7 = sign8(((r7 + 0x48) & 0xff) ^ 0x11)
    obj9[r6] = r7
    r6 += 1

r1 = 0
while r1 < r2:
    index = [0, 1][r1]
    r7 = obj9[index]
    r7 = sign8(((r7 + 0x26) & 0xff) ^ 0x20)
    obj9[r6] = r7
    r1 += 1
    r6 += 1
```

The second block is the same structure with the two transforms swapped:

```text
alphabet at 0x170 -> VIPII_ALPHABET_21
first loop:  +0x26 then xor 0x20
second loop: +0x48 then xor 0x11
```

`signature_algorithm.py` now includes `vipii_generate_token(seed, length, mode)`
with a pure-Python glibc `rand()` model.  For the observed header call this is
expected to be `length == 4`, producing two random alphabet-derived bytes plus
two bytes derived from output indices 0 and 1.

## LLIJL progress

The call chain for the second nested VM is now clear:

```text
sub_5B6D9EB(...)
  -> sub_5B61D31(key8, 8, a9, rc4_output, rc4_output_len)
  -> sub_5B61848(format="LLIJL", ...)
  -> sub_5B62F7E argument loader
  -> sub_5B64F10 on VM_PROGRAM_LLIJL
```

`sub_5B62F7E` treats the first format byte as a return marker.  For `"LLIJL"`,
the active argument characters are therefore `"LIJL"`; because `J` consumes two
VM slots, five VM slots are initialized.  `sub_5B636DE("LLIJL") == 5`, and
`VM_PROGRAM_LLIJL[0:2] == 0x1b`, so argument slots start at `0x1b - 5 == 22`:

```text
r22 = L object: key8 object (8 bytes)
r23 = I integer: 8
r24/r25 = J value: native a9 64-bit value split/loaded as two slots
r26 = L object: RC4 output object
```

This matches the early LLIJL bytecode using `r22`, `r23`, and `r26`:

```text
0010: r0 = ... r23 ...
0014: r1 = clone(r26)
...
006c: r7 = obj[r22][r7]
```

The high-level structure of `VM_PROGRAM_LLIJL` is also clearer:

1. Compute `ceil(r12 / 4)` where `r12` is derived from input length.
2. Allocate an 8-entry int array (`r14`) and a per-block int array (`r9`).
3. Loop over 4-byte chunks from `r22`, packing bytes into 32-bit words using
   shifts `24/16/8/0` style operations.
4. Initialize/clear the 8-entry state array.
5. Process output in 64-byte rounds (`r10 += 64`) with a byte packing loop that
   writes four bytes per word into a temporary byte object (`r5`).
6. XOR bytes from `r1` and `r5` and store into output object `r3`.

Additional opcode confirmations from the LLIJL path:

* `0x0b`: modulo of two scalar registers, stores into `r[dst]`.
* `0x29`: 32-bit scalar copy/truncate (`r[dst] = *(int32*)&r[src]`).
* `0x2a`: qword scalar copy.  Examples: `2a120700` means `r18 = r7`, and
  `2a071800` means `r7 = r24`.
* `0x2b`: qword array load from an object.  Example: `2b080b06` means
  `r8 = ((uint64_t*)obj[r11].data)[r6]`.
* `0x30`: object store variant.  In LLIJL it stores the per-block qword into
  `obj[r9][r5]` or clears `obj[r14][r5]`.
* `0x46`: conditional branch on non-zero scalar; LLIJL uses it to choose
  `ceil(n/4)` versus `n/4`.

This makes the central region look like a word-schedule/mixing routine:

```text
for each 4-byte key chunk:
    word = (key[i*4+0] << 24) | (key[i*4+1] << 16) |
           (key[i*4+2] <<  8) | (key[i*4+3] <<  0)
    schedule[i] = word

state[0..7] = 0

for offset in range(0, output_len, 64):
    tmp_words = state/schedule mixing using r24/r25 and helper op_72
    pack tmp_words to bytes in big-endian byte order
    output[offset+i] = input_obj[offset+i] ^ tmp_bytes[i]
```

More helper recovery:

* `0x06`: dword add form.  The handler reads two 32-bit scalar slots and stores
  their sum into the destination slot encoded in the first VM word.
* `0x1b`: dword copy/move form.  The handler copies a 32-bit scalar from the
  source slot encoded by `((word >> 9) & 0x78)` into the destination slot.
* `0x1c`: qword right-shift form.  It reads a 64-bit scalar and shifts by an
  `int32` scalar from another slot.
* `0x72`: fixed native helper call.  It fetches objects/slots 5, 6, 7, and 9 and
  calls `sub_5B6CFF4(obj5.data, obj6.data, slot7_payload, slot9)`.  This is the
  main remaining black box in the LLIJL mixing routine.

The unresolved core is now mainly `sub_5B6CFF4` plus the exact alignment around
the late sequence:

```text
09871677 81000d77 ff000f77 3107030a
```

The VM switch only has explicit cases through `0x7c`, so `0x81`/`0xff` are likely
not intended standalone opcodes in a valid execution path, or they are reached
through an instruction-length/operand encoding nuance still to recover.  The next
step is to decompile/analyze `sub_5B6CFF4` and its inputs.

## sub_5B6CFF4 is ChaCha20 core

`sub_5B6CFF4` has been decompiled and identified as a standard ChaCha20 block
function:

```text
state[0..3]   = "expand 32-byte k"  # xmmword_990380 at 0x990380
state[4..11]  = 32-byte key buffer passed as a2
state[12..13] = a4 as two little-endian u32 words
state[14..15] = a3 as two little-endian u32 words
```

It runs 10 double rounds with rotations `16, 12, 8, 7`, then adds the original
state words back into the working state.  `signature_algorithm.py` now includes:

```python
chacha20_block_64_64(key32, counter64, nonce64)
chacha20_xor_64_64(data, key32, counter64, nonce64)
```

The LLIJL nested VM is therefore building a 32-byte ChaCha key buffer and using
`a9` plus the current block offset/counter as the 64/64 counter-nonce tail.
What remains is to map exactly how the 8-byte `key8` and the VM schedule/state
populate the 32-byte `a2` buffer before each `sub_5B6CFF4` call.

The earlier zero-key interpretation is disproved.  Assembly for `sub_5B61D31`
shows the exact call boundary into the nested VM:

```text
5b61ed5  rsi = key8 ArgBlock
5b61ef2  edx = n8
5b61ef5  rcx = salt64
5b61ee1  r8  = src ArgBlock
5b61ef8  r9d = src_len
5b61efd  call sub_5B61848("LLIJL", keyblock, n8, salt, srcblock, src_len)
```

The bytecode reads from the key object while constructing a packed key-word
object:

```text
006c: 32 07 16 07      load from obj[r22][...]
008e: 32 07 16 07      load from obj[r22][...]
00b2: 32 07 16 07      load from obj[r22][...]
00d8: 32 07 16 07      load from obj[r22][...]
```

After repacking, the words are copied into `r14`, an eight-word object.  Before
opcode `0x72`, the VM executes `r6 = clone(r14)`.  Opcode `0x72` then uses fixed
slots and passes object slot 6 as `a2`:

```c
sub_5B6CFF4(r5.data, r6.data, r7, r9)
```

and `sub_5B6CFF4` copies `a2[0..31]` into ChaCha state words 4..11.  For the
observed native call `sub_5B61D31(key8, 8, ...)`, this key buffer is:

```python
key32 = key8 + b"\0" * 24
```

The block setup at `0x0108..0x0126` prepares:

```python
counter64 = block_offset // 64
nonce64 = salt64
sub_5B6CFF4(block.data, key32, nonce64, counter64)
```

`signature_algorithm.py` now models LLIJL as ChaCha64/64 XOR using that key32,
counter, and nonce.

The helper is deliberately named `tentative` because native comparison is still
needed to prove that the separate `key8` schedule has no hidden effect on the
ChaCha key buffer or output packing.
